# O03 VM・アプリ状態の復元

> **更新日** 2026-09-12 ・ **区分** 開発計画 ・ **読む人** 開発者

**区分**: 運用整備・実機確認 ・ **状態**: VM復元補助ツールあり、アプリ横断の復元合格を整備する。

## 目的・現状・配備先

VMとアプリ状態を失っても、Git・外部state・バックアップから隔離復元し、利用を再開できるようにする。[復旧方針](../architecture/operations.md)と`tools/pve-restore-drill.sh`に別VMIDへの演習手段がある。ツールの存在だけを各アプリの復元合格とは扱わない。

## 変更範囲と実装

1. VM所有state、イメージ、DB、原本、設定、暗号鍵、SSO鍵、USB／GPU割当を対象ごとに一覧化する。原本・状態・stateの正本とコピー先を分け、同一SSD上のVMコピーを物理障害対策と数えない。
2. [W03](W03-nextcloud.md)はDB・設定・ファイル、[W02](W02-vaultwarden.md)はDB・添付・鍵、[A01](A01-pokemon-ai.md)は両DB・WebUI状態、[H01](H01-home-assistant.md)はContainer設定・履歴・秘密・機器割当を整合単位として扱う。AWXのDB・暗号鍵・PVC、NetBox、identity、Garage、etcdも復元一覧に含める。
3. 利用可能な既存外部コピー先と鍵の独立保管を確認し、対象ごとの復元元を記す。保存先未確定は独立した前提条件として残し、ハード増設を要求しない。
4. 既存ツールで別VMIDへ戻す際は、起動前にNIC・IP・外部連携を隔離する。新VMIDが基盤・cloud APIの予約範囲や所有stateと衝突しないことを確認する。テスト環境から家電操作、Bot送信、定期ジョブを発動させない。
5. 復旧は外部Tailscale／管理LAN → Proxmoxと外部state → 必要なストレージ・identity・services-01 → cloud-01／Kubernetes → 各依存DB・アプリの順に、依存する範囲だけ進める。各独立アプリの復元演習を一列の実施待ちにしない。
6. 本番切替は復元合格後に名前・IP・接続を切り替える。切替後の新しい書込を保全してから戻す。削除は演習対象と確認したものだけに限定し、元のデータは合格前に消さない。

## 依存と並列作業

- **開発開始:** 復元一覧・手順・模擬試験は独立作成できる。
- **実機演習:** 対象アプリの整合バックアップ、外部鍵、[I01](I01-resources.md)の容量、[N02](N02-tailscale.md)の復旧経路が必要。管理DBは[O01](O01-cloud-backup.md)、CNPGは[O02](O02-cnpg-backup.md)の成果を使う。
- **競合:** 大容量復元のI/O、VMID・IPの確保、ホスト停止、state import、DNS切替は同時操作を調整する。各アプリ担当が自分の復元結果を持ち、共通一覧には結果と依存だけを集約する。

## 検証・完了条件

Gitだけでは戻らない状態と鍵を含め、隔離環境で再起動・ログイン・代表データ・権限・アプリ連携を確認する。停止したVMから別機能へ影響が及ぶ範囲を実測し、外部コピーだけで復元できた対象を区別する。実測の復旧時間・失う可能性のある期間・最後の成功日・残る外部条件を記録し、本番を壊さず演習を片付けられる。
