# N01 セルフホストVPN

> **更新日** 2026-09-23 ・ **区分** 開発計画 ・ **読む人** 開発者

**区分**: 新規実装・外部条件確認 ・ **状態**: 計画作成済み、配備未実施。

## 目的・現状・配備先

普段の宅外接続をセルフホストVPNで提供する。配備先は **services-01内の独立Compose**。VPN専用VMは追加しない。[VPN比較](../architecture/vpn.md)はNetBirdを第一検証候補としているが、回線・ルータの外部到達と認証入口は未確認。[identity](../operations/identity.md)を再利用し、別の認証基盤は作らない。

## 変更範囲と実装

1. `stacks/vpn/` にNetBirdの設定、版固定、秘密値の例、配備・停止・復元手順を作る。公式の対象版と既存Caddyの構成を確認し、HTTP/UDP入口・中継・保存先を一覧化する。
2. VPNのCompose名・永続領域を他サービスと分ける。services-01全体の4vCPU／8GiBは共用予算で、VPNへ丸ごと割り当てない。
3. 現在のidentityのOIDC設定に合わせ、一般利用グループから許された内部サービスだけへ接続する。招待・端末承認・紛失端末の失効・復旧管理者を分ける。
4. 初回登録・再認証にVPN自身を必要とする循環を避ける。まずLAN／復旧用Tailscaleから登録する運用で検証し、外部認証入口を使う場合のみ到達条件と公開範囲を確定する。
5. NetBirdでPC・スマホ各1台を検証する。必須条件を満たせない場合は失敗理由を記録して製品選定を更新し、複数製品を同時に常用配備しない。

## 依存と並列作業

- **開発開始:** 他IDの完了待ちは不要。模擬OIDC・ローカル設定検証を先行できる。
- **実機配備:** [I01](I01-resources.md)のservices-01余力確認、[N02](N02-tailscale.md)の独立復旧経路、回線・CGNAT・転送設定・DNSの確認が必要。外部入口を集約する場合のみ[N04](N04-public-edge.md)と接続条件を合わせる。
- **回線の前提（[N06](N06-router.md)の実測）:** MAP-E（v6プラス）で **80/443 は使えない**が、割り当て済みの240ポートを使えば **WireGuard の公開は可能**。NetBird の公式quickstartが前提にする 80/443 到達はこの回線では満たせないため、選定時の重みが変わる。Tailscale の待ち受けを割当内のポートに固定すると直接接続が成立しやすく、Moonlightの遅延改善も見込める。開放は数個に留める（外向き通信と共有するため）。
- **競合:** services-01の80/443、共通TLS設定、identityのOIDC設定、ルータのポート転送を[N05](N05-https.md)と調整する。VM再起動は[H01](H01-home-assistant.md)・[W01](W01-homarr.md)・[W02](W02-vaultwarden.md)・NetBox・文書利用者に影響する。

## 検証・完了条件

- 宅外で許可されたサービスへ接続でき、Proxmox・DBの管理経路は一般利用者へ開かない。
- PC／スマホのスリープ復帰、Wi-Fiとモバイルの切替、通常VPNとTailscaleの切替後にDNS・ルートが正しい。
- services-01停止中にも `net-01` の subnet router 経由でホスト管理へ入れる（K11そのものの停止はカバーしない）。identity停止中の既存セッションと再認証の挙動を記録する。
- 設定・DB・鍵・端末登録を隔離環境で復元し、失効端末が再接続できない。構成チェック合格と実機合格を別々に記録する。
