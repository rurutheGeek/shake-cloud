# N04 公開Web入口

> **更新日** 2026-10-12 ・ **区分** 開発計画 ・ **読む人** 開発者

**区分**: 新規実装 ・ **状態**: **完了（2026-10-05）。ただし当初案とは別の形で実現した。**

**計画していた `public-edge` VM（Caddyの公開入口）は作りませんでした。** 回線で 80/443 が開けないという前提（下記）が解けなかったため、公開は**宅外の中継機を経由する形**に変え、公開サイトそのものを載せる `web-01` を作りました。手順・実測・残件の正本は[公開サイト](../operations/web.md)、方針は[決定ログ](../architecture/decisions.md)の「公開サイトの出し方」です。このページは**そこへ至るまでの検討**として残します。

| 当初案 | 実際 |
| --- | --- |
| `platform/terraform/services/public-edge/` に入口VMを作る | `platform/terraform/services/web/` に**サイト本体のVM `web-01`** を作った。入口を分けていない（nginx が自分でTLSを終端する） |
| ルータの 80/443 転送で受ける | **家庭回線には着信を開けない。** Cloudflare → 宅外の中継機 → tailnet → `web-01` |
| 入口から上流（内部サービス）へ中継する | 内部サービスは公開しない。公開するのは `web-01` の4サイトだけで、**`web-01` から自宅LANへは戻らせない** |

## 目的・現状・配備先

**前提が1つ確定している。回線は MAP-E（v6プラス・JPNE）で、割り当てられた 240 個のポートしか開けられず、そのなかに 80/443 は含まれない**（[N06](N06-router.md)の実測）。つまり `https://名前/` の形で公開することはこの回線ではできない。公開が要るなら、外部のリバースプロキシ／トンネルを併用するか、別回線を用意するかの判断が先になる。

公開するWebが決まった時点で、内部サービスへの許可経路だけを持つpublic-edgeを追加する。[配置設計](../architecture/operations.md)の候補は1vCPU／1GiB／OS16GiB。現有ホスト上のcloudプールへ作り、現時点ではVM宣言・DNS・ルータ転送を適用しない。内部WebのHTTPS整備は[N05](N05-https.md)で独立して進める。

## 変更範囲と実装

1. 公開対象、FQDN、転送先、必要な認証、WebSocket等の接続条件を対象ごとに記録する。**回線の外部到達性は調査済み**（上記のMAP-E制約）なので、80/443 を前提にした設計は採らない。未指定のサービスを公開しない。
2. `platform/terraform/services/public-edge/`を配備条件確定後に実装し、shakecloud ProviderでVMとSGを管理する。単独stateとし、基盤VMを取り込まない。
3. Caddyの設定・証明書状態を永続化し、入力は必要なHTTP(S)、出力は選定した上流のみ許可する。上流の管理ポートやDBへの到達を与えない。
4. DNS所有と証明書更新を[I04](I04-cloud-dns.md)に合わせ、外部URLと上流URLのリダイレクト・Cookie・認証コールバックを確認する。公開経路の停止だけで戻せる切替手順を作る。

## 依存と並列作業

- **開発開始:** 公開対象未確定でも入口のテンプレート・模擬上流による試験表を作れる。
- **実機配備:** 公開対象と外部到達条件の確定、[I01](I01-resources.md)の余力、[I05](I05-service-state.md)のstateが必要。DNS切替は[I04](I04-cloud-dns.md)と行う。VLANの採否は[N03](N03-vlan.md)と整合させるが、N03全完了を開発の前提にしない。
- **競合:** ルータ80/443、[N01](N01-vpn.md)の認証・中継入口、DNSレコード、証明書発行を調整する。同じ名前を20-dnsとサービスstateで所有しない。

## 検証・完了条件

当初の完了条件は「外部端末でTLS・認証・想定リクエストが成功し、未指定ホスト名と管理先は拒否される。DNS・転送の撤回で公開を停止できる」でした。**実際に満たした形は[公開サイト](../operations/web.md)の「守り」と「検証」**です（SGの既定拒否、ゲスト内nftablesによるLAN宛80/443の遮断、TLS1.1拒否とセキュリティヘッダ、他VMへ届かないことの実測）。公開の停止は、中継機の向き先を戻すか `web-01` を止めることで行います。

残っているのは次の2つで、どちらも[公開サイト](../operations/web.md)が正本です。

- 入口を core-01 の Caddy へ寄せる（いまは `web-01` の nginx が自分で終端）
- shake-infra 側のCD（旧ホスト向けのまま）の整理

Tailscale の ACL による絞り込み（`tag:relay` → web-01 の 80/443 だけ）は **2026-10-05 に適用済み**です。
