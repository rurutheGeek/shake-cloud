# I04 クラウドVMのDNS登録

更新日: 2026-09-12。区分: **新規統合**。状態: 基盤DNSは実装済み、サービスVMのライフサイクル連携は未実装。

## 目的・現状・配備先

サービスVMの作成・交換・削除に追従する名前管理を用意する。既存`platform/terraform/20-dns/`は`dns.yaml`と05-seed／10-platformの出力からAレコードを作る。クラウドVMの自動登録がないことは[サービス運用](../operations/services.md)に記載済み。

## 変更範囲と実装

1. **基盤名は20-dns、サービスVMの名前はそのサービスstate**が所有する。media等のモジュール内でCloudflare ProviderのDNSレコードをVMの確定IP出力へ接続する。クラウドAPIにDNSの公開APIや権限を追加しない。
2. サービス名は宣言で指定し、tags.Nameだけから勝手にDNSを作らない。LAN用Aレコードは現行と同じ非プロキシ・TTL300を初期値とし、公開入口は[N04](N04-public-edge.md)で公開対象を確定する。
3. VM置換は新IP・TLS・アプリの健全性確認後にDNSを切り替える。停止だけでは名前とIP予約を維持する。削除時はレコードを除去してからIP解放し、TTL経過を含め旧IPへの接続を抑える手順を作る。
4. APIやポータルでstate外から削除された場合も想定し、配備前のrefreshとDNS照合で不在・IP変更を検出する。APIの即時DNS自動回収はこの方式では提供しないため、サービスVMの通常削除は所有state経由と明記する。緊急削除時はDNS担当が直ちに同期する。
5. 既存20-dnsレコードを移す場合は変更窓でimport／state移管し、同一レコードの二重所有と削除・再作成を避ける。DNS用資格情報は対象zoneに限定し、VM内へ配布しない。

## 依存と並列作業

- **開発開始:** Terraform定義・模擬出力・操作手順を独立して作れる。
- **実機登録:** [I05](I05-service-state.md)の共有state、対象VMの確定IP、DNS資格情報が必要。[I02](I02-media-vm.md)との接続後に切替を確認する。
- **競合:** 同じ名前の20-dnsとサービスstate移管は単独担当で行う。[N05](N05-https.md)のTLS、[I03](I03-cloud-inventory.md)のIP照合、[N03](N03-vlan.md)のサブネット変更と調整する。DNS設定とCaddy上流設定は別物として両方検証する。

## 検証・完了条件

作成・無変更再apply・停止再開・VM交換・削除・手動削除後の検出を試し、旧IPや孤立レコードが残らない。既存基盤レコードへ差分がなく、LAN／VPNからTLS名と正しい上流が一致する。DNS失敗時はアプリ切替を止め、元のIP／レコードへ戻せる。
