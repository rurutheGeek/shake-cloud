# G03 ゲームとAIの負荷調整

> **更新日** 2026-09-12 ・ **区分** 開発計画 ・ **読む人** 開発者

これは開発計画であり配備完了の記録ではありません。[配置・所有境界・並列作業の共通ルール](index.md)を参照してください。番号は実施順を表しません。

## 目的・現状

**状態**: 運用改善・実機検証

[ゲーム設計](../architecture/gaming.md)では12GiB固定から開始し必要なら16GiB、ゲーム中はOllama停止を想定している。今回AI・DB・Botもgame1へ同居するため、新しい負荷実測と停止粒度が必要。

配備先・開発範囲: **game1とホストの観測。開発範囲は `stacks/game/` の運用手順と関連AI設定の上限調整**。

## 実装手順

1. ゲームのみ、AIのみ、DB/検索のみ、ゲームと常駐サービス併用の測定項目を揃える。RAM/VRAM・CPU・I/O・温度、配信フレーム落ち・音切れ・推論応答を記録する。
2. 12GiBの実測を基準に、必要なら既存所有経路で16GiBへ変更する。ホスト・他VMの余力をI01で確認し、固定RAMをバルーニング回収見込みへ含めない。
3. ゲーム開始時に新規推論と取り込みを停止し、実行中処理を終える/中断してモデルを解放する操作を用意する。DB・軽い検索・Botは負荷に応じて維持するが、停止中の推論へ無限再試行させない。
4. AWX・走査・開発ビルドの現実的な併用負荷も加えて上限を調整する。測定結果から許容する組み合わせ・停止対象・再開方法を一覧化する。

## 依存と並列作業

- 開発開始: なし。測定様式と観測用手順は各機能の完成前に用意できる。
- 配備・切替: 各組み合わせの試験対象[G01](G01-wolf.md)/[G02](G02-azahar.md)/[A02](A02-ollama.md)の準備。[I01](I01-resources.md)とホスト全体の予算を共有する。
- 競合調整: 性能試験中の大規模ビルド・走査・バックアップを記録/調整する。並列開発そのものの待ち条件にはしない。VM再起動は全game1利用者と調整する。

## 検証・完了条件

- 対象作品の30〜60分試験で実行速度・音声・配信の基準を記録し、AI停止前後の改善と再現性を示す。
- メモリ不足・推論失敗時も基盤VMやホストを不安定にせず、負荷停止と復帰を操作できる。
- 再起動後も採用した上限が反映され、モデル解放/再開、DB状態保持、Botの処理不能応答を確認する。
