# N03 VLAN切替

> **更新日** 2026-09-12 ・ **区分** 開発計画 ・ **読む人** 開発者

**区分**: 既存実装の実機確認・運用切替 ・ **状態**: 宣言・手順あり、物理切替未実施。

## 目的・現状・配備先

管理LANを維持したまま、cloudプールの利用者VMをタグ付きVLANへ移す。[既存切替手順](../operations/vlan.md)に、ルータ・スイッチ、VLAN aware bridge、宣言、API再配備、切り戻しがある。APIのVLAN検証とVM NICへのタグ設定を新規未実装とは扱わない。

## 変更範囲と実装

1. 現有ルータ・スイッチの対応、トランク設定、空きVLAN ID、既存アドレスとの重複、物理コンソールを確認する。機器購入を本計画の代替にしない。対応しなければ外部条件待ちとして現行LANを維持する。
2. `network.yaml`を正本にcloud側のVLAN・サブネットを定め、管理側はタグなしを維持する。既存手順の例示アドレスは実値確認後に利用する。
3. 必要通信を列挙し、一般VMからProxmox・管理DB・Garage管理APIへの到達を制限する。管理・IoT・公開入口の全面再編はこの切替へまとめない。
4. 使い捨てVMで作成・SSH・SG・削除を確認してから、game1等を利用者と調整して移す。クラウド管理DB・NetBoxのIP予約・ゲスト設定・DNSを一組として更新し、旧IPを先に再割当しない。
5. 既存手順へ確認結果、操作前退避、切り戻し条件を反映する。

## 依存と並列作業

- **開発開始:** 設定差分、通信表、試験、資料は独立着手できる。
- **実機切替:** 物理設備の対応・コンソールと[N02](N02-tailscale.md)の復旧経路が必要。VMごとに容量・停止時間を[I01](I01-resources.md)と確認する。
- **競合:** `network.yaml`、`10-platform` state、API再配備、ルータ・bridgeの変更は単独担当で適用する。[I03](I03-cloud-inventory.md)・[I04](I04-cloud-dns.md)と旧IP除去を調整し、ゲームの試験と同時にgame1を再起動しない。

## 検証・完了条件

管理到達性、使い捨てVMのタグ・新IP・SG、内部サービスの許可通信、禁止通信を実測する。切替後も既存VMのクラウド所有者が変わらず、DNSとインベントリに旧IPが残らない。切り戻しでNIC・API設定・IP予約・DNSが一致し、利用を復旧できる。
