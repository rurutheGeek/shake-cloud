# eufyCam S4 のライブ映像を Home Assistant へ安定反映する（依頼書）

> **更新日** 2026-10-03 ・ **区分** 開発計画 ・ **読む人** 開発者

> **2026-10-03の注記**: 解析作業は中断中。関連スタック（eufy-security-ws・eufy-leo-rtc・Home Assistant）はapps-01で稼働する。以下の「services-01」は当時の配備先（2026-10-03にapps-01へ移設）。

## 1. 依頼の要旨

eufyCam S4（T8172、有線給電・HomeBase なし）のライブ映像を、**Home Assistant の
カメラで実用になる品質（滑らかで途切れない）で見られるようにしてほしい。**

現状は「静止画がたまに更新される」だけで、動画として成立していない。
HA には `camera.eufycam_s4_leo_rtc`（RTSP/HLS 経路・不安定）と
`camera.eufycam_s4_mjpeg`（MJPEG 経路・約 1.3fps でビタビタ）の 2 つがあるが、
**どちらも実用品質に達していない。**

## 2. いま出来ていること（実測）

| 段 | 状態 | 根拠 |
| --- | --- | --- |
| カメラの wake〜ICE〜KCP〜メディア受信 | できる | セッション 1 回で 2,000〜6,900 パケット |
| 捕捉の完全性 | 良い | `incomplete=0`・IDR 6/6 復号（受信バッファ 32MB 設定後） |
| IDR・パラメータ・音声の復号 | できる | AES-128-GCM（カメラの `sdp_info` の鍵） |
| RTSP 配信（Mediamtx） | 条件付き | 1 セッションの映像がある間だけ publish。〜40〜50 秒/70 秒周期 |
| HA の HLS 再生 | **不可** | `camera/stream`（HLS のみ対応）でプレイリストが出ない |
| HA の MJPEG 再生 | 遅い | `camera_proxy_stream` で 6 秒に 8 フレーム（約 1.3fps） |
| エンティティの可用性 | 時々落ちる | `unavailable` で UI がライブを開始できない（自動 reload を実装済み） |

## 3. 原因（分かっていること）

1. **カメラは 1 接続あたり 10〜30 秒で映像を止める。**
   アプリ（純正）は数分〜連続で視聴できるので、**アプリは何かでセッションを維持している**。
   最有力は `0xce`（内側 `f1 ce`）レポートで、**約 24 回/秒**送っている。
   我々は現状 DRWAck（`f1d1`）と XZYH 0x473 心拍のみで、これが揃っていない。
2. **RTSP/HLS 経路が短命な配信の繰り返しになっている。**
   HA のストリームワーカーは再接続ごとにバックオフを伸ばし、窓を外し続ける。
3. **MJPEG 経路は毎回「捕捉全体を一括変換」して 1 枚作るため遅い。**
   一括変換は正しい（今夜の不具合修正で画質は完全）が、速度が約 1.3fps しか出ない。
4. HA 2026.9 の `camera/stream` は **HLS のみ**（WebRTC は指定不可）。generic/mjpeg
   統合は UI 専用で、設定は `.storage` へ書いて入れる必要がある（対応済み）。

### 今夜すでに直したもの（再発防止のため記録）

- services-01 の `net.core.rmem_max`（既定 416KB → 32MB。欠落の真因）
- コンテナの ffmpeg 5.1 → 静的 7.0.2（パイプ入力の HEVC で参照を落とす）
- 断片の遅延到着に 12 フレームの確定遅延（`LEO_FRAME_LAG`）
- カメラの解像度切替で libx264 が -22 → 出力 1280x720 固定＋パディング
- HA のカメラ設定が古い VM の URL のままだった（`172.31.254.1` へ修正）
- デマンド検知のパス名・ログオフセットずれ
- `unavailable` の自動 reload（systemd timer・2 分毎）

## 4. 依頼する作業（優先順）

1. **`0xce`／`f1 ce` レポートの自前生成（本命）**
   - 構造は判明済み: 外側 `f1 ce <BE16 長>` の本体に、CS2 暗号化された内側 `f1 ce`
     フレームが複数（on-wire では `b0 ce…`）。内側の記録は
     `0d <subtype> <BE16 長> <時刻 BE32> …` と `06 <SSRC 4B> <seq BE16> …`（9061 と 902f の ack）。
   - 未解読: 記録のビットマップの意味（どの seq 範囲をどう詰めるか）。
   - ゴール: 自前で組み立てて約 24 回/秒送り、**1 セッションを数分維持**する。
2. **滑らかな配信**
   - 第一候補: 1 が効けば RTSP が長命になり、HA の HLS がそのまま動く。
   - 第二候補: MJPEG の高速化（捕捉の差分変換で 5〜10fps）。一括変換は 1 回
     `incomplete=0` で正しいので、増分だけ変換する実装に変える。
3. **補助調査**（1 が難航した場合）
   - アプリは TURN（`75.2.46.73:3478`）経由でメディアを流している。直経路との差の確認。
   - `c0c9`／`90 ce` 系アプリ送信の役割。

## 5. 受入条件（この状態になったら完了）

- HA のカメラで**連続 30 分以上、途切れずに映像が流れる**（≥ 5fps）。
- 黒・灰・緑の単色フレームが出ない（今夜の修正で満たす見込み。要再確認）。
- 音声（AAC-LC 16kHz）も同時に再生できる。
- カメラが一時的に落ちても **10 秒以内に自動復帰**する。
- 既存のイベント通知・Push・スナップショット（H04 の `eufy-security-ws`）を壊さない。

### 8.2 実測で分かったこと

- **1 セッションの映像はカメラ時刻で約 11 秒で止まる。** 送出量（画質）にも経路にもよらない。
  60 秒のセッション（3,341 パケット）に映像 134 フレーム（約 12fps）だけ。
- **再 wake を詰められない。** 間隔 3〜5 秒だとカメラが応答しなくなる（映像 0 が続く）。15 秒以上が必要。
  このため現状は「1 分強のうち約 10 秒だけ動く」。
- **公式アプリは TURN 中継（75.2.46.73:3478）経由で映像を受けている**（pair2.pcap: 映像 24,198 パケットすべて ChannelData）。
  自前でも TURN 経由の受信は成立したが、**同じく約 11 秒で止まった**。経路は原因ではない。
- **固定 RTCP は原因ではない。** アプリの `81c9` は標準の RR（拡張最大 seq が現在値）＋REMB＋XR。
  動的に組み立てて映像中に送っても長さは変わらなかった。
- KCP でアプリが定常的に送るのは 0x473 心拍のみ（自前も送信済み）。
- 残る差は、アプリが中継経由で送る独自のフィードバック（`b0ce`／`90ce`、PT 78 系）。
  この解析は 2026-10-01 未明に中断した（再開しない）。
- **android-01（Waydroid）の公式アプリは現在ライブを開けない**（`Connection failed`）。
  起動したままにするとカメラを取り合い、自前のセッションも映像 0 になる。**使ったら必ず
  `am force-stop com.oceanwing.battery.cam`**。Waydroid の audioserver が固まったときは
  `waydroid-container`／`android-env` の再起動で戻る。

## 9. 追記（2026-10-01 昼・アプリ捕捉の解析）

### 9.1 実機スマホからの再採取は不可（経路のため）

実機スマホ（Wi-Fi・Tailscale ON）で**本物のライブ（音あり）**が見えている状態で
router-01（OpenWrt）に tcpdump を張ったが、**カメラ↔スマホの映像は 1 パケットも
通っていなかった**（カメラの通信はクラウド 443 への制御 1.5 pkt/s のみ、スマホは
TURN のキープアライブ 146 パケットのみ）。原因は **router-01 に無線が無い**こと
（`br-lan` は eth1 のみ＝Wi-Fi AP は別機器）。LAN 内の端末間映像はルータを通らない。

→ 追加採取は「①VM アプリの復活（品質設定の巻き戻し等）②スマホでの PCAPdroid」の
どちらか。ただし **Waydroid のアプリは画面に映像が出たことがない**（メディアは流れた）。

### 9.2 既存の完全なアプリ捕捉（pair2.pcap）でフィードバックを全解読

app→camera の内訳（60 秒、TURN 中継越し・平文で観測可）:

| 種別 | 回数 | 内容 |
| --- | --- | --- |
| `b0ce` | 1,409（23.5/s） | **CS2 暗号化された受信レポート**（`f1ce`）。復号すると `d1 <counter> <BE32 時刻> …` と `06 <SSRC 4b> <seq BE16>`（= 9061/902f の ack） |
| `90ce` | 241（4/s） | **同じ内容の平文版**（RTP 風ヘッダ PT=78）。暗号不要で読める |
| `81c9`→`c0c9` | 267（4.5/s） | 復号すると `c0 c9 …`：標準 RR（拡張最大 seq）＋REMB＋XR（既実装・効果なし） |
| `80c9` | 59（1/s） | `80 09 00 01 00 00 00 01` の 8 バイト心拍 |
| `9ecc` | 59（1/s） | ANKExV4 の空 keepalive |

- レポートは**ラップ構造**: 外側 `f1ce` の本体に、次の（または相方の）`b0ce` ブロックが
  入れ子で入る。同一パケットに 2 ストリーム分の ack が入ることもある（長さ 148〜352 で可変）。
- **ack は「その瞬間の受信最大」より約 70 パケット古い**（例: 受信 max 29972 に対し
  レポートは 29902）。ビットマップ様の可変部（`00 41 42 00 40 …`）がどの範囲をどう
  表すかが未解読で、**これが自前生成の最後の壁**。
- 注目: `90ce` は**平文**なので、テンプレート化して自前の seq を入れる実装が最短。
  ただし可変部の意味を確定しないと以前のテンプレ生成のようにカメラが止まる恐れ。

### 9.3 次の一手（推奨）

1. `b0ce`/`90ce` の可変部（ビットマップ）を、同じ pcap の**受信 seq 列と突き合わせて**
   解読する（カメラ不要・純解析）。→ 解読できたら自前生成して 4〜23/s で送り、
   セッションが伸びるか実測。
2. 並行して、現状の relay 運用（常時 publish・HLS は動作）で「動く秒数/分」を最大化する
   調整（wake 間隔・`LEO_VIDEO_IDLE`）。

### 9.4 レポートの実装仕様（2026-10-01 昼の解析で確定した分）

`pair2.pcap` の `90ce`（平文）と `b0ce`（CS2 復号後）を突き合わせた結果:

- **`90ce` は平文のレポート**。RTP 風ヘッダ（`90 ce` = PT 78）で、
  `90 ce | BE16 | f0fe | BE16 | <時刻 BE32> | 01 20 02 61 4e 01 | 06 <SSRC 4b> <seq BE16> | <状態バイト列>`
  の形。復号後 `b0ce` も同じ本体を持つ（外側 `f1ce` の本体先頭 `d1 <counter> <時刻 BE32> …`）。
- **時刻は実クロックではなく固定ステップのカウンタ**: 連続レポートで **+0x101 ずつ**増える
  （実測: 3a714cd1 → 3a714dd3 → 3a714ed4 → …）。自前生成では同じステップで模倣できる。
- **状態バイト列は「直近の約 10 パケット」の状態**（0x40/0x41/0x43 系のバイトが並ぶ。
  226 パケット/秒 ÷ 23.5 レポート/秒 ≈ 9.6 個とほぼ一致）。レポートの長さが 148〜352 と
  可変なのはこの列の長さのため。ロスが無ければ同じ値が並ぶので、テンプレート＋自前の
  時刻・seq で「全受信」のレポートを組める見込み。
- `81c9`（=復号後 `c0c9`）は RTCP（RR＋REMB＋XR）で実装済み（効果なし）。`80c9` は 8 バイト心拍、
  `9ecc` は ANK の空 keepalive。
- **最短の実装**: `90ce`（平文）をテンプレート化し、①時刻カウンタ（+0x101 ステップ）
  ②`06 0dc1a815 <seq>` を自前の受信 seq ③状態バイトは全受信 に置き換えて
  **4〜23 回/秒**送る。効果測定は 1 セッションの映像長（現在約 4〜11 秒）で判定。

（注意: 以前テンプレートを自前値で埋めた試みはカメラが映像を止めた。値の整合
[時刻と seq の対応] を崩さないこと。失敗しても 15 秒後の再 wake で復帰する。）

### 9.5 実装と効果測定（2026-10-01 13:00）

- `tools/leo_live.py` に `LEO_APP_REPORT=1`（テンプレートは `/state/report_templates.json`）で
  **アプリ平文レポート（`90ce`）の自前送信**を実装（20 回/秒、時刻は +0x101 ステップ、
  `06 0dc1a815 <seq>` は自前の最終受信 seq、状態バイトはテンプレートのまま）。
- **効果（同一環境の前後比較）**:
  - 前: 1 セッションの映像 中央値 **約 4.1 秒**（500 パケット前後が最頻）
  - 後: 中央値 **約 9.9 秒**、最大 **14.0 秒**（5,600 パケット）。10 セッション中 8 が 9 秒以上。
  - 一過性に 0.2〜0.4 秒のセッションが 2 回出たが、その後は回復（約 2 倍の延長効果）。
- つまり**アプリのレポートはセッション維持に効いている**。受け入れ条件（30 分連続）には
  未達だが、リレーと合わせて「動く割合」は約 1.5〜2 倍になった。
- 次の調整候補: 送信レート（アプリ実測は `90ce` 4/s・`b0ce` 23.5/s の合計約 27/s）、
  状態バイト列（全受信 vs テンプレート）、時刻カウンタの初期値。

### 9.6 アプリとの直接比較と「アプリ準拠」構成（2026-10-01 15:00-16:00）

同一の分類器で「アプリのセッション（pair2.pcap）」と「我々のセッション（our.pcap）」を
突き合わせた（単位: パケット/秒）。

| 方向 | 種別 | アプリ | 我々（変更前） |
| --- | --- | --- | --- |
| cam→client | 映像(9061) | 248 | 27 ※セッションが短いため |
| cam→client | 902f(PT47) | 132.5 | 1.3 |
| cam→client | 音声 | 20.5 | 3.3 |
| client→cam | `b0ce`（暗号レポート） | **23.8** | **0** |
| client→cam | `90ce`（平文レポート） | 4.1 | 3.0 |
| client→cam | `81c9`（RTCP） | 4.5 | ライブ中は約4 |
| client→cam | KCP | 2.1 | 同等 |
| client→cam | **`b0d1`（DRWAck）** | **0** | **1.8** |

分かったこと:

- **アプリは `f1d1`（DRWAck）を一切送らない**。我々の `b0d1` はアプリに存在しない送信で、
  カメラに未知の信号を送っていた可能性が高い。
- アプリは **暗号形レポート（`b0ce`）23.8/s ＋ 平文（`90ce`）4.1/s** の二本立て。
  我々は平文しか送っていなかった。
- `902f`（PT47・同 SSRC・同 ts/seq を共有・1 seq に 1200B×8〜9 個）は序盤に多く漸減する
  （740→298 /5s）。アプリは 132/s 受けるが我々は 1.3/s しか受けない。
- 我々の送信は「ライブ中」のレートを見ると KCP・RTCP・STUN とも概ね一致していた
  （セッションが短いため時間平均が小さく見えていただけ）。

**採用（アプリ準拠構成）**: `LEO_DRWACK=0`（DRWAck 廃止）＋ `LEO_REPORT_ENCRYPT=1`
（暗号形 24/s）＋ 平文 4/s。実測で **1 セッションの映像が中央値 11 秒・最大 18.8 秒**に
改善（変更前は 4〜14 秒、DRWAck 有り・平文のみ）。

残る差: `902f` の受信量と、暗号形レポートの内部（入れ子ブロック）の時刻カウンタ。

### 9.7 最終ソーク（2026-10-01 16:00-17:00）

- アプリ準拠構成で 1 時間連続運転。セッション中央値 **9.2 秒**・最大 10.8 秒

### 9.9 続き（2026-10-02 日中）— ICE ロールの配備漏れと連続性の検証

- **ICE ロール修正がコンテナへ渡っていなかった（重大）**: `.env` には
  `LEO_ICE_CONTROLLED=1` があったが **compose.yaml の environment に項目が無く**、
  コンテナ内は既定（CONTROLLING）のままだった。このため我々の STUN は 0x802a＋
  USE-CANDIDATE のままカメラに 487 Error を返され、ICE1（KCP チャネル）が成立して
  いなかった。compose に `LEO_ICE_CONTROLLED: ${LEO_ICE_CONTROLLED:-1}` を追加して
  初めて controlled になり、**カメラの Error 応答が消え、ICE1 が成立、カメラから
  我々への KCP push が届く**ようになった（実測: 108〜160B・接頭辞末尾 conv=3）。
- KCP ACK をアプリ実測（`52 00 ff 01 <ts> <受信 sn をエコー> <una=sn+1>`）に合わせた
  — セッション長への効果は見られず（中央値 18.5 秒のまま）。
- **同一セッション内の映像復帰は不可**: 映像停止後に 1003 をメディア（ANK）と KCP の
  両経路へ 3 秒間隔で再送（counter も毎回更新）。12 秒版・**60 秒版（20 回）**とも
  映像は再開せず。カメラは同一セッションでの再開要求を受け付けないと判断。
- **TURN 経由は映像ゼロ**: `LEO_TURN=1`／`LEO_TURN_MODE=only` では relayed 候補は出るが
  映像パケットが 1 つも来ない（セッション 0.0 秒）。既定の直経路（off）へ戻した。
- **eufy-security-ws は無関係**: 数分停止してもセッション長は不変（干渉なし）。
- **並行セッションは可能だが連続起動は不可**: 第 2 クライアントを別ソケットで同時に
  走らせると、第 1 が生きていても映像を取得できる（実測 2,895 パケット）。ただし
  短い間隔（約 10〜20 秒）で次々に起きると **カメラが新規セッションを無視**し始め
  （0 パケットが連発、バックオフが 300 秒まで上昇）。重なり起動の supervisor 実装は
  撤回し、1 本ずつ起こす現行方式に戻した。起床間隔はカメラの許可（体感 40〜100 秒）
  が支配的で、詰めると逆効果。
- 日中（10-02）のセッション統計: 映像 8,000〜10,000 パケット／**中央値 20〜24 秒**・
  最良 25.2 秒。`LEO_DEMAND_WAIT=5` は機能する（視聴中は 5 秒後に次の起床を試行）。
- 未解決の本丸: アプリの「何時間でも」の仕組み。直結構成のカメラは 1 セッション
  20 秒前後で映像を止め、同一セッション内の再開を受け付けないため、現状は
  relay の最終フレーム保持で見た目を繋いでいる。
- **解析上の注意（10-02 訂正）**: これまで UDP 先頭 4 バイトを長さとして除去していたが、
  KCP にはその 4 バイトが無く、解析結果が 4 バイトずれていた。生ワイヤを直接確認した
  結果、我々の KCP は **32B 接頭辞（`01 00 00 00`＋`01 00 00 00`＋20 ゼロ＋
  `01 00 00 00`）＋20B ヘッダ＋ペイロード** で、コンテナ実装（`kcp_prefix`）と一致。
  カメラ側は接頭辞の 2 番目が 0・末尾が 3 の形式。以前の「28 バイト接頭辞」観測は
  この解析バグによるもの。送信形式の修正は不要だった。
- 視聴中の待機（`LEO_DEMAND_WAIT=5`）でも失敗時のバックオフを尊重するよう修正
  （失敗中に 5 秒間隔で連打するとカメラが無視するため）。
- **再武装（同一プロセスで映像復帰を粘る）は逆効果**: 映像停止後も KCP/socket を温存し、
  15 秒間隔で新しい calls＋1003 を送る実装（`LEO_REARM_LIMIT`）を試したところ、開始
  直後からカメラが新規セッションを無視（0 パケット連発）。撤回し既定 0 に戻した。
  カメラが許容する wake は**おおむね 25 秒以上・同時 1 本**が上限と判断（8 秒重なり
  起動・15 秒再武装とも拒否された）。失敗時のバックオフは視聴中も尊重する。
- **TURN 中継は修正後は機能する**: KCP（32B 接頭辞＋20B ヘッダ）と ICE-CONTROLLED の
  修正後、`LEO_TURN=1`（mode=only）で **TURN 経由の映像受信に成功**（`TURN relayed`
  → `media peer set (turn)`、1 セッション 7,900〜9,300 パケット＝約 20〜23 秒）。
  ただしセッション長は直結と同じで、カメラ側の 20 秒前後の制限は中継でも変わらない。
  LAN 内の HA には直結（既定 `LEO_TURN=0`、WAN 帯域を使わず低遅延）が適切。TURN は
  宅外・WAN 経由が要る場合の選択肢として残す。

### 9.10 続き（2026-10-02 夜）— 「映像が実質映っていない」の真因と修正

- **真因（relay のデコード破損）**: `tools/mjpeg_bridge.py` の `iter_annexb` が、最初の
  IDR の直前に **古いパラメータセット（VPS/SPS/PPS）を差し込んでいた**。カメラは
  セッション中に解像度（レンズ）を切り替えるため、差し込まれた古い SPS/PPS と実際の
  スライスが食い違い、relay の出力（RTSP/snapshot）が色ノイズ・灰色の破損映像に
  なっていた。パラメータはワイヤどおりその場にだけ流す方式へ修正し、オフライン
  検証（`packets_to_annexb` と同一の分類）と実機の RTSP フレームで**実画像**を確認
  （カメラ OSD の時刻＝撮影時刻でライブ）。**HA 上で「映像が動かない」の主因は
  この破損だった**。
- **HA の見え方を修正**: ユーザーのダッシュボード/習慣が指す `camera.rihinku` は
  eufy 統合側の **S4 ライブ非対応**エンティティだった。エンティティ登録を入れ替え、
  `camera.rihinku` = 自前ライブ（RTSP/HLS）、旧 eufy 側は `camera.rihinku_eufy`
  （名称「リビング (eufy・ライブ非対応)」）に退避。Overview の先頭に
  `camera_view: live` のカメラカードを追加（`lovelace/config/save`）。
- **再起床の間隔**: `LEO_WAKE_WAIT=12`（既定 25 → 12 秒）へ短縮。失敗が続くときは
  demand 中でもバックオフを尊重（連打はカメラに無視される）。
- **実測（ブラウザ相当の HLS 視聴を継続、4 分）**: snapshot が変化したのは **31% の
  時間**（おおよそ「約 20 秒の実映像 → 約 40 秒静止」の繰り返し）。カメラは 1 回の
  ライブで 20〜24 秒しか映像を出さず、次の付与まで約 40〜60 秒かかる（同一セッション
  内の復帰・短間隔の再起床は拒否される）ため。**アプリの「何時間でも」はクラウドの
  ライブサービス側の仕組み**と推定し、次の大物として残す。
- **映像中の 1003 定期再送・fresh calls は不可（10-02 深夜）**: 映像が流れている最中に
  1003（メディア/KCP）を 10 秒ごとに再送してもセッション長は伸びない（約 20 秒のまま）。
  さらに映像中の fresh calls は **逆効果でセッションが 0.3 秒に破壊**された（即撤回）。
  直結・TURN とも「1 回の付与＝20〜24 秒・次の付与まで約 40〜60 秒」がカメラ側の上限。
- **アプリのクラウド映像は真に連続（確定）**: pair2.pcap の中継映像を解析すると、
  59.3 秒間で RTP ts が 59.1 秒分進み、ストリーム再開は無い（ts リセットなし）。
  20 秒制限は我々の直結セッション種別に対するもので、**アプリは eufy クラウドの
  ライブサービス経由で連続配信を受けている**。次はアプリのクラウド live API の
  再現（APK 解析資産: `jadx-full`・`solibs` は保持）に着手する。

### 9.11 深夜の追試（2026-10-03）— 直結の上限確定とクラウド経路の再確認

- **上流SDKの調査**: `@mega-yfue/eufy-sdk`（移植先）の `live-stream.ts` は
  `DEFAULT_KEEPALIVE_MS=3000` でライブ中 3 秒ごとに `startLiveMedia`（keepalive）を送る。
  クラシック P2P のバッテリー機には「45 秒 + 猶予 10 秒」の**クライアント側**自動停止
  （`budget` 通知 → `extend()`）があるが、これは我々の 20 秒制限とは別物。SDK 自身も
  「素の 1139 心拍で中央値 ~5000 datagram（約 20 秒）」と記録しており、**直結の
  20 秒前後は我々固有の不具合ではない**（配線機でも同じ）。
- **深夜に試して不可だったもの（全て撤回）**: 映像中の 1003 定期再送（10 秒間隔）、
  映像中の fresh calls（セッションが 0.3 秒に破壊）、`LEO_DRWACK=1`（14 秒へ短縮）、
  映像停止時の closeLive(1004)（次セッションが乱れる）。
- **アプリ送信の全解読（pair2）**: アプリ→カメラの中継側（TURN ChannelData）は
  RTCP(81c9)・90ce・b0ce のみで KCP/ANK は無く、**KCP は直結**（VM↔CAM 284 パケット）。
  送信量は約 35/s で我々と同等。周期的な独自 keepalive は見当たらない。
- **公式 Web クライアントの再試行（不可）**: `hally/` の Web 実装（署名・WSS・P2P を
  webrtc_bundle.js から移植したもの）を復旧して実行。ログイン/署名/WSS/SCTP は
  通るが、call は `100` → **`408`**（カメラ無応答）。直結パイプラインを止めても同じ。
  S4 は Web の WebRTC call に応答しない（既知の結論を再確認）。
- **結論**: アプリの「何時間でも」は **クラウド側のライブサービス**（カメラ↔クラウドの
  常時接続側でセッションを管理）であり、我々が観測できる直結/TURN の範囲外。次の一手は
  カメラのクラウド接続側の捕捉・復号か、クラウド API の live 開始エンドポイントの特定。
  現状の直結は「1 回 20〜24 秒・視聴中は約 60 秒周期」がカメラ側の上限。
- 現行の推奨設定: `LEO_WAKE_WAIT=12`・`LEO_DRWACK=0`・`LEO_CLOSE_1004=0`・
  `LEO_1003_KEEP=0`・`LEO_CALL_KEEP=0`・`LEO_TURN=0`・`LEO_ICE_CONTROLLED=1`。
- **レポート有無の A/B（13:25-13:45）**: アプリ相当のレポート（90ce/b0ce 等）を止めても
  セッション長は約 25 秒（レポートありの約 24 秒と同等）。**レポートはストリーム維持の
  必須条件ではない**（アプリ準拠のため既定は ON に戻した）。
- 直結の上限 ~20〜25 秒に対する残りの仮説は「カメラとスマホアプリの直結/クラウドの
  どちらか」。切り分け方法: **ユーザーがスマホのアプリでライブを見ている最中に、
  こちらからセッションを張る**。並行して成立すればアプリはクラウド経由（衝突しない）、
  不成立ならアプリは直結でカメラの 1 クライアント枠を占有している（＝直結でも長時間が
  可能で、我々に何かが欠けている）と判定できる。

### 9.12 クラウド経路の再現調査（2026-10-03）

- **アプリのクラウド中継は TURN そのもの**: pair2 の全映像は `75.2.46.73:3478` の
  ChannelData（アプリ側の Send indication の宛先は「カメラの公衆マッピング」）。
  我々の TURN セッションも捕捉検証で **映像 6,586 パケットが relay 経由**であることを
  確認済み（誤解していた「直結に戻っている」は無し）。
- **アプリ側クライアントの送信は我々と同等**: relay 経由の **2.5 秒ごとの ICE
  binding request（consent）**、RTCP(81c9)・90ce・b0ce の報告、直結 KCP 心拍。
  独自の延長コマンドは無い。
- **バイト同一の calls 再送（5 秒間隔）**を実装して検証 → セッションは 24〜26 秒
  （最大 10,419 パケット）で有意な延長なし。fresh calls が壊すのと対照的に無害だが
  効果も無いため既定 0 に戻した。
- **結論**: カメラ→relay の区間でアプリのストリームが 59 秒以上連続するのに対し、
  我々のセッションは ~25 秒で止まる。両者のクライアント側パケットはほぼ同一なので、
  差は **クラウド側のライブセッション管理（サーバ側で開始・維持）**にあり、これは
  TLS／サーバ内で観測不能。公開実装（bropat/Web）もこの live を持たない。
  クラウドのライブサービス自体を再現するには eufy サーバ側の資格・API が必要で、
  現状のカメラ直結/TURN クライアントでは到達できない。
