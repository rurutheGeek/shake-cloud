# O01 管理DBの外部バックアップ

> **更新日** 2026-09-16 ・ **区分** 開発計画 ・ **読む人** 開発者

**区分**: **既存バックアップの拡張**。状態: ローカル保存・timer・**最終成功時刻のメトリクス（M01で監視）**実装済み。外部保全を整備する。

## 目的・現状・配備先

cloud-01やK11の喪失時にも管理DB・配備状態を戻せるようにする。[クラウド運用](../operations/cloud.md)と`cloud/manage.py`にpg_dump形式のバックアップと配備ファイル保存があり、systemd timerは毎日03:40・14世代を既定にする。新しくDBダンプ機構を作り直さず、成功した世代の外部コピー・検証・復元を追加する。

## 変更範囲と実装

1. 現行バックアップの最終成功・サイズ・世代・復号に必要な情報を確認する。DBだけでなくcompose・環境設定・secrets等が含まれるため、転送先と鍵へのアクセスを限定する。
2. 既存の外部S3互換先または既存別機器の利用可能な容量・権限を確認し、独立した保存prefixへ暗号化して転送する。保存先が未確定なら外部条件待ちとして記録する。ハードウェア購入やK11内Garageだけを外部コピーの代替にしない。
3. 完了した世代だけをアップロードし、検証後に成功扱いとする。転送失敗はローカル世代を失わせず、最終成功日時と失敗を運用へ見せる。**ローカルの最終成功時刻はnode_exporterのtextfile collectorへ1行出し、36時間停滞と欠測をアラートにする（実装済み。cloud-backup.serviceの`ExecStartPost`＋`manage.py backup-metric`、閾値は`stacks/monitoring/prometheus/alerts.yml`）。**保持はまず14日相当を開始値とし、外部容量と復旧要件に合わせて記録する。
4. 隔離した管理DBへ復元し、アカウント・インスタンス・IP対応・ジョブ・監査記録を照合する。APIを実インフラへつながない状態で検証し、古いジョブの再実行やリソース再作成を防ぐ。
5. [O03](O03-restore.md)へ、復元時点以降のProxmox／NetBoxとの照合と再開手順を渡す。バックアップ保存成功と復元合格を分けて管理する。

## 依存と並列作業

- **開発開始:** 転送処理・fixture・復元手順は保存先確定を待たずに作れる。
- **外部転送:** 保存先・暗号鍵の独立保管・運用権限の確定が必要。stateの保管先と同じ基盤を使う場合も[I05](I05-service-state.md)とはprefix・権限を分ける。
- **競合:** backup timer・cloud_apiロール・管理DB復元は単一担当で反映する。[I01](I01-resources.md)と容量・I/O、[O03](O03-restore.md)と復元窓を調整する。サービス配備中の世代境界を明記する。

## 検証・完了条件

正常転送、切断、資格情報失効、保存先容量不足、再実行を確認し、失敗で有効な世代を消さない。K11内の原本にアクセスせず外部コピーと独立保管鍵から復元できる。最終成功日時と復元試験日、実測した復旧所要時間を記録する。
