## 3. 重大（P1）

### 3.1 SOPS の age 受信者が 1 本しかない ★最優先

- `.sops.yaml` の 2 ルールとも受信者は `age1r6y7am...` の 1 本。
- 暗号化済み **21 ファイル**すべてが同じ 1 鍵（`recipient:` の実測）。第1版時点の 13 から増えた。
- `.sops.yaml` 自身のコメントが「少なくとも利用者2人ぶんと自動実行用を並べます」と指示しているのに、従っていない。

この 1 鍵を失うと Proxmox root・Cloudflare・NetBox 書き込み・k8s SA・SMTP・S3・**monitoring** のトークンが一括で復号不能になります。バックアップから戻しても復号できないので、§3.2 を直しても復旧できません。`secrets.md` の「`~/.config/sops/age/keys.txt` と外部コピー」は同じ鍵の 2 コピーであって冗長化ではありません。

```bash
age-keygen -o ~/offline-backup.agekey   # オフライン保管（紙 or 別媒体）
age-keygen -o ~/automation.agekey       # AWX/CI 用
# .sops.yaml の age: をカンマ区切り3本へ
sops updatekeys platform/sops/*.sops.yaml platform/flux/**/*.sops.yaml
```
`tests/test_sops_config.py` が受信者一覧の一致を検査するので、更新漏れはテストで落ちます。**30分で終わり、失うもののサイズが最大。**

### 3.2 バックアップが実質存在しない

- スケジュール実行されるバックアップは `cloud/cloud-backup.timer.j2`（毎日03:40・14世代）**の1本のみ**。保存先は `/var/backups/cloud-api` = cloud-01 自身 = K11 の同じ SSD。ロールの既定値にも「ディスク故障対策にはならない」と自分で書いてある。
- identity/Authentik・NetBox・Vaultwarden・Homarr・Home Assistant・media 各種・romm は `manage.py backup` を持つが、**timer を配るタスクが存在しない**（`roles/*/tasks/main.yml` で backup を扱うのは `cloud_api` と `cups` のみ）。
- Garage・etcd・Proxmox ホスト自身の定期 vzdump は仕組みがない。`tools/pve-restore-drill.sh` は良いツールだが手動の単発ドリル。

SSD が死ぬと、Git のコード・宣言・手順は残りますが、**Authentik のユーザーと鍵、NetBox の台帳、Vaultwarden の保管庫、管理DB、Garage、etcd、そして Grafana/Prometheus の履歴が全部消えます。**

対策の順:
1. 外付け媒体を Proxmox storage に登録し、全基盤 VM を週次 `vzdump --mode snapshot`（全損 → 1週間前）
2. restic + R2（state とは別 prefix・別トークン）で家の外へ。O01 の「保存先未確定」はこれで閉じる
3. PostgreSQL は pg_dump、SQLite は `.backup`。方針は既に文書にあるので timer に落とすだけ
4. `pve-restore-drill.sh` を月1、**最終復元成功日**を `handover.md` に1行で持つ
5. **バックアップの成否をメトリクスにする**（§4.1-3）

### 3.3 既定セキュリティグループが全許可で、管理面と同一 L2

最新 main でも変わっていません。

- `securitygroups.go:65-71` — 既定 SG は in/out とも `0.0.0.0/0` `::/0` の `all`（コメントも "allows all traffic"）
- `firewall.go:122-125` — SG が 0 個のインスタンスは **Proxmox ファイアウォール自体を `enable=0`**（完全無フィルタ）
- VLAN 分離（Phase 8）は物理作業待ちで未実施

同じ L2 上に Proxmox（:8006）、NetBox（:8000 **平文**）、identity、cloud-01 の管理DB、そして**新たに monitor-01（Prometheus :9090・Alertmanager :9093）と各VMの node_exporter :9100、print-api :6320（平文 bearer）**が載りました。監視スタックが増えたぶん、この L2 に置かれた口が増えています。

EC2 の既定 SG は少なくとも外からの inbound を閉じています。「AWS の語彙に揃える」という本プロジェクトの方針からも外れています。

VLAN の物理作業を待たずにできること:
1. 既定 SG の ingress を空（または同一 SG 内のみ）にし、egress は all のまま
2. それが運用上きついなら、**管理 CIDR への egress DROP を既定 SG の先頭に**。`renderFirewall` は ACCEPT しか生成しないので小改修が要る
3. SG 0 個で無フィルタへ戻れる分岐を塞ぐ（デタッチ時に既定 SG を必ず残す）

## 4. 高（P2）

### 4.1 監視スタックに残る 4 つの穴

配備済みであることを踏まえた上での指摘です。**どれも「監視が無い」より直しやすく、効果が大きい**ものです。

**(1) node_exporter を5台から収集しているのに、`node_*` を使うアラートが1本もない。**
`alerts.yml` の 5 本は `probe_*` / `pve_*` / `network_ups_tools_*` だけです。VM 内のディスク満杯・メモリ枯渇・OOM Kill・systemd unit の失敗・予期しない再起動は、**メトリクスは取れているのに通知されません。** 収集済みなので、ルールを足すだけで済みます。

```yaml
- alert: NodeFilesystemAlmostFull
  expr: node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes < 0.10
- alert: NodeMemoryPressure
  expr: node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes < 0.10
- alert: SystemdUnitFailed
  expr: node_systemd_unit_state{state="failed"} == 1     # --collector.systemd が要る
- alert: NodeRebooted
  expr: time() - node_boot_time_seconds < 600
```

**(2) Dead man's switch がない。** monitor-01 が落ちる／Prometheus が落ちる／Alertmanager が落ちる／Gmail が弾く — **いずれも「静かになるだけ」で、静かなことと正常なことが区別できません。** 定番は、常時 firing する `Watchdog` アラートを外部へ送り続け、外部側で「一定時間来なかったら異常」と判定する形です。

```yaml
- alert: Watchdog
  expr: vector(1)
  labels: {severity: none}
```
受け先は healthchecks.io の ping URL か、ラズパイ側の Uptime Kuma の Push monitor。**monitor-01 は cloud VM = K11 上なので、監視対象と同じ故障ドメインにいます。** 設計文書が「監視は既存ラズパイと連携する」と書いているのは、まさにこの点です。最低限の死活だけでもラズパイ側に置く価値があります。

**(3) バックアップの成否がメトリクスになっていない。** §3.2 の timer が失敗しても誰も知りません。node_exporter の textfile collector に1行吐くのが定石です。

```bash
# バックアップスクリプトの末尾
echo "backup_last_success_timestamp_seconds{job=\"cloud-api\"} $(date +%s)" \
  > /var/lib/node_exporter/textfile/backup.prom.$$ && mv ... backup.prom
```
```yaml
- alert: BackupStale
  expr: time() - backup_last_success_timestamp_seconds > 36*3600
```
これが入ると §3.2 の 1〜4 が「やったつもり」にならなくなります。**バックアップを増やす前に、これを先に入れるのを勧めます。**

**(4) 通知経路が Gmail 1本。** しかも**停電時は monitor-01 ごと K11 の上で落ちます。** `UpsOnBattery` は「送信が間に合えば届く」程度の保証しかありません。モバイルプッシュ（ntfy/Pushover）の追加と、UPS 起因の通知だけはラズパイ側から出す設計を検討する価値があります。

軽微: `route.group_by` が `[alertname]` のみなので、複数ホストの `ServiceProbeFailed` が1通にまとまります。`[alertname, instance]` のほうが読みやすいです。

### 4.2 UPS が「見えるだけ」で、自動停止しない

`roles/pve_nut/tasks/main.yml` の冒頭に明記されているとおり、**入っているのは `usbhid-ups` + `upsd`（状態を読む側）だけで、`upsmon`（低電池で止める側）は未有効**です。`upsd.users.j2` も監視ユーザーに FSD 権限を与えていません。M01 の「残りは低電池シャットダウン」がこれです。

現状は「停電に**気づける**が、**止まらない**」。バッテリーが尽きた瞬間に、PostgreSQL（管理DB・Authentik・NetBox・CNPG）と SQLite（Vaultwarden・Kavita）を抱えたホストが電源断します。§3.2 のバックアップが無い状態と重なると最悪です。

`power.md` に「安全な電源の切り方」の順序（AWX/非同期ジョブ確認 → `tools/k8s down` → ホスト `shutdown -h now`）が既にあるので、**その知識をそのまま `SHUTDOWNCMD` に落とすだけ**です。

```
# /etc/nut/upsmon.conf
MONITOR ups@localhost 1 upsmon <pass> master
SHUTDOWNCMD "/usr/local/sbin/shakecloud-power-down"   # tools/k8s down 相当 → shutdown -h now
```
M01 の完了条件どおり、隔離環境で手順を確認してから有効化するのが正しい進め方です。**UPS を買って挿した時点で仕事の半分**で、残り半分がここです。

### 4.3 NetBox の書き込みトークンが平文 HTTP を流れる

`http://192.168.10.200:8000` への参照が 11 箇所（`netbox.sops.yaml.example`・`cloudapi.sops.yaml`・bootstrap.md・handover.md ほか）。`https://netbox.apextox.dpdns.org` が既にあるので、**接続先をそちらへ統一し、8000 は 127.0.0.1 へ戻す**のが素直です。§3.3 により同じ L2 に利用者 VM がいるので、書き込みトークンが取れる構図になっています。

**同種**: `print-api` が `PRINT_API_BIND=0.0.0.0`、bearer トークンを平文 HTTP で受けます（`roles/cups/tasks/main.yml:207`）。IP 許可リスト（`192.168.10.101`）はありますが、同じ L2 では気休めです。Caddy 経由か 127.0.0.1 + トンネルへ。

### 4.4 NetworkPolicy が 1 つもない

`platform/flux/` に NetworkPolicy / CiliumNetworkPolicy が無いままです。とくに **`functions` namespace は Knative で利用者のコードが動きます**。Cilium は入っているので default-deny（egress は DNS と明示先のみ）は安価です。`operations.md` に「NetworkPolicy を設定する」と書いてあるので、意図と実装のギャップです。

### 4.5 コンテナのメモリ制限がゼロ

全 `compose*.yaml` に `mem_limit` も `deploy.resources` もありません。**monitor-01（2GiB）に Prometheus・Grafana・Alertmanager・blackbox・pve-exporter・nut_exporter・PeaNUT の 7 コンテナが載った**ので、この指摘の重みが増えました。Prometheus は保持期間とカーディナリティ次第でメモリを食うので、`mem_limit` と `--storage.tsdb.retention.size` の併用を勧めます。**監視が OOM で落ちるのは、監視が無いより質が悪い**（静かになるだけなので。§4.1-2 と対になります）。

ホストは割当合計 60.1GiB > 物理 59.7GiB のオーバーコミット状態で、そこへ monitor-01 2GiB が増えています。

### 4.6 Cloudflare の DNS 編集トークンが全ホストに配られている

`roles/tls_proxy` が各ホストへ `cloudflare_dns_api_token` を置き、各 Caddy が DNS-01 で証明書を取ります。**1台侵害 = ゾーン全体の DNS 書き換え権限**。分散の理由（identity を他ホストの障害に巻き込まない）は妥当なので、対策は分散をやめることではなく:
- トークンを Zone:DNS:Edit でこのゾーンだけにスコープ（既にそうならそれを明記）
- `_acme-challenge` の CNAME 委譲（acme-dns 等）で DNS 編集権限そのものを配らない
- 最低限、ローテーション手順と最終ローテ日を `handover.md` に持つ

### 4.7 依存更新の自動化が無い（文書は Renovate 前提）

`.github/` に `renovate.json` も `dependabot.yml` もありません。一方 `operations.md` と `00-bootstrap/versions.tf` のコメントは「Renovate の PR で更新を確認する」と書いています。**digest 固定＋更新の仕組み無しは「固定されたまま古くなる」**。CI に脆弱性スキャン（`govulncheck` / `pip-audit` / `trivy`）もありません。Go が本体なので `govulncheck ./...` を1ステップ足すのが最も費用対効果が高いです。

## 6. 良い点（維持すべき設計）

- **`handover.md` の「確定した決定」表**。理由と実測（Proxmox の 403 が「無い」を意味しない、チャンク転送 501、ルール挿入が pos 0、`/tmp` が tmpfs）まで残る。引き継ぎ資産としてリポジトリで最も価値が高い。
- **監視の作り方が正しい**。Grafana のデータソース・ダッシュボード・アラートをファイルでプロビジョニングし、「monitor-01 を再作成しても同じ画面に戻る」を完了条件にしている。`tests/test_monitoring_stack.py` が blackbox のターゲットと `dns.yaml` の一致を検査するので、名前を足して監視を足し忘れる事故が起きない。**「監視を後から入れた」プロジェクトにありがちな手作りダッシュボードになっていない。**
- **OpenAPI を正本にし、Go のルート表との一致を `routes_test.go` で強制**。生成をしない判断とその代替検証がセット。
- **noVNC を CDN ではなく同梱**（sha512 照合・無改変・`PROVENANCE.md`・CSP `script-src 'self'`）。
- **コンソールの防御**: Cookie 認証の WebSocket に Origin チェック（`CrossOriginProtection` が GET を見ないことを理解した上での追加実装）、5分トークン、メモリ上もハッシュ、ログに出さない、`no-store`。
- **`tools/check-publication.py`**: 実 `.env`・secrets から needle を作って staged blob を検査し、未暗号化 `.sops.yaml` と鍵パターンも弾く。CI で毎回走る。
- **`.gitignore` が deny-by-default**（`platform/sops/*` を全除外し3種だけ否定パターンで追跡）。
- **Terraform state を R2 へ**（ミニPCの SSD に依存させない）＋ `use_lockfile = true` ＋ backend に事業者固有値を書かず `tools/tf` が SOPS から渡す。
- **`tools/pve-restore-drill.sh`**: 復元先の NIC を切断してから起動、既存 VM を消さない、cleanup だけ確認を求める。
- **CI の網羅**: 823 の Python テスト、全 tracked YAML のパース、Terraform fmt/validate（全 root module）、gofmt、go vet、go test（実 Postgres 付き）、yamllint、公開チェック、mkdocs --strict。
- **UPS の読み取りユーザーに FSD 権限を与えていない**（`upsd.users.j2`）。権限を最小にする習慣が細部まで一貫している。

## 7. 推奨する着手順（改訂）

監視が入ったので、順序が変わります。**「気づける」は概ね済んだので、次は「戻せる」と「止まる」です。**

| 順 | 作業 | 見積 | 効果 |
| --- | --- | --- | --- |
| 1 | age 受信者を3本にして `sops updatekeys`（3.1） | 30分 | 鍵喪失による全損を消す |
