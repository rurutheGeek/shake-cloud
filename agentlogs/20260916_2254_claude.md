## 2. 総評

**ホームラボとしては明確に上位。** 「決定を文書に残す」「正本を1か所に定める」「手作業を増やさない」という原則が、掛け声ではなく実際のコード・テスト・CI に落ちている。特に `docs/operations/handover.md` の「確定した決定」表は、個人のホームラボでは滅多に見ない水準で、実測値と根拠（Proxmox の 403 の意味、チャンク転送 501、ルール挿入位置が 0 になる等）まで残っている。

一方で、**評価の軸が「作る」に寄っていて「壊れたあと」に寄っていない。** 機能（VM・S3・DB・関数・SSO・ポータル・CLI・Provider）は揃ったが、それを支える 4 つ（バックアップ・監視・電源・鍵の冗長）が揃っていない。以下の指摘はほぼすべてそこに集中する。

なお、以下の多くは本人も文書中で「未完了」「保存先未確定」と自覚している。**自覚と、実際に夜中に起きたときの復旧可能性は別物**なので、優先順位の提案として書く。

## 3. 重大（P1）— ここから着手すべき

### 3.1 バックアップが実質的に存在しない

**事実:**
- リポジトリ内でスケジュール実行されるバックアップは `cloud/cloud-backup.timer.j2`（毎日 03:40、14 世代）**のみ**。
- その保存先は `cloud_api_backup_dir: /var/backups/cloud-api` = **cloud-01 自身のディスク = K11 の同じ SSD 1 枚**。`roles/cloud_api/defaults/main.yml` にも「ディスク故障対策にはならない」と明記済み。
- 他スタック（identity/Authentik、NetBox、Vaultwarden、Homarr、Home Assistant、media 各種、romm）は `manage.py backup` を持つが、**timer/cron を配る仕組みがない**。手で叩かない限り一度も取られない。
- Garage（storage-s3）・etcd（k8s-cp-01）・Proxmox ホスト自身の定期 vzdump は仕組みが存在しない。`tools/pve-restore-drill.sh` は良いツールだが**手動の単発ドリル**。
- `docs/architecture/operations.md` の「バックアップと復旧」は方針のみ、`O01` は「保存先未確定なら外部条件待ちとして記録する」。

**評価:** 現状で SSD が死ぬと、Git にあるコード・宣言・手順は残るが、**Authentik のユーザーと鍵、NetBox の台帳、Vaultwarden の保管庫、管理DB、Garage のオブジェクト、etcd は全部消える。** Git からの再構築では戻らないと自分で書いているとおり。これは「未完了の TODO」ではなく**単一障害点そのもの**。

**提案（順番どおりにやる）:**
1. **今週中の暫定**: USB 外付け HDD を K11 に挿し、Proxmox の storage として登録。`vzdump --mode snapshot` を全基盤 VM に対して週次で回す。これだけで「全損」が「1週間前に戻る」になる。
2. **次**: 外部（家の外／別媒体）へ。R2 を既に使っているので、`restic` + R2 バケット（state とは別 prefix・別トークン）が最短。O01 の「外部保存先未確定」はここで解ける。
3. **アプリ整合性**: PostgreSQL は pg_dump、SQLite（Vaultwarden・Kavita・Navidrome）は `.backup` かサービス停止。**ファイルコピーだけで取らない**方針は既に書いてあるので、それを timer に落とすだけ。
4. **定期ドリル**: `pve-restore-drill.sh` を月1で回し、`handover.md` に「最終復元成功日」を1行で持つ。**バックアップの成否より復元の成否を記録する**。
5. 各 `manage.py backup` を配る systemd timer は `cloud-backup.timer.j2` と同じ形で横展開できる。既に雛形がある。

### 3.2 SOPS の age 受信者が 1 本しかない

**事実:**
- `.sops.yaml` の `creation_rules` は 2 ルールとも受信者が `age1r6y7am...` の **1 本だけ**。
- 暗号化済み 13 ファイル（`platform/sops/*` 12 + Flux の 2）すべてが同じ 1 鍵で暗号化されている（`recipient:` の実測で確認）。
- ところが **`.sops.yaml` 自身のコメントに**「特定の1人の鍵でしか復号できない状態にしないため、少なくとも『利用者2人ぶん』と『自動実行用』を並べます」と書いてある。**自分のルールに自分が従っていない。**

**評価:** この 1 鍵を失うと、Proxmox root トークン・Cloudflare API トークン・NetBox 書き込みトークン・k8s ServiceAccount トークン・SMTP・S3 アクセスキーが**全部まとめて読めなくなる**。バックアップから戻しても復号できないので、3.1 を直しても復旧できない。`docs/operations/secrets.md` は「`~/.config/sops/age/keys.txt` と外部コピー」と書いているが、それは同じ鍵の 2 コピーであって冗長化ではない（片方が古い／同じ引き出しにある等の事故に弱い）。

**提案:**
```bash
age-keygen -o ~/offline-backup.agekey      # 2本目（紙 or 別媒体・オフライン保管）
age-keygen -o ~/automation.agekey          # 3本目（AWX/CI 用。将来の自動実行）
# .sops.yaml の age: をカンマ区切り 3 本にする
sops updatekeys platform/sops/*.sops.yaml
sops updatekeys platform/flux/**/*.sops.yaml
```
`tests/test_sops_config.py` が受信者一覧の一致を検査しているので、更新漏れはテストで落ちる。**この作業は 30 分で終わり、失うもののサイズが一番大きい。**

### 3.3 既定セキュリティグループが「全許可」で、管理面と同一 L2

**事実:**
- `cloud/api/internal/compute/securitygroups.go` の `EnsureDefaultSecurityGroup` は、ingress・egress とも `0.0.0.0/0` `::/0` の `all` を入れる（コメントにも "allows all traffic" と明記）。
- `firewall.go` の `applyFirewall` は、SG が 0 個のインスタンスに対して **Proxmox ファイアウォール自体を `enable=0` にする**（完全無フィルタ）。
- VLAN 分離（Phase 8）は**物理作業待ちで未実施**。利用者 VM は管理面と同じネイティブ VLAN に載っている（handover.md の決定表・`docs/operations/vlan.md`）。
- 同じ L2 上に Proxmox（192.168.10.126:8006）、NetBox（192.168.10.200:8000、**平文 HTTP**）、identity、cloud-01 の管理 DB が居る。

**評価:** ポータルにログインできる利用者が、**既定設定のまま VM を1台作るだけで、管理面へ到達できる足場を得る。** EC2 の既定 SG は「同一 SG 内からの inbound のみ許可／outbound 全許可」で、少なくとも外からの inbound は閉じている。ここは EC2 の語彙に揃えるという本プロジェクトの方針からも外れている。「以前からそうだったので互換のため」というコメントの理由付けは、**利用者が増える前提のセルフサービス基盤では通らない**。

**提案（VLAN の物理作業を待たずにできる）:**
1. 既定 SG を EC2 準拠に変える: egress は all 許可のまま、**ingress は既定で空**（または同一 SG 内のみ）。
2. それが運用上きついなら、最低限 **管理 CIDR（Proxmox・NetBox・identity・cloud-01・k8s API）への egress DROP ルールを既定 SG の先頭に入れる**。`renderFirewall` は ACCEPT しか生成しないので、DROP を先頭に積む小改修が要る。
3. SG が 0 個のとき firewall を無効化する分岐（`applyFirewall` の `len(ids) == 0`）は、**そもそも SG 0 個になれないようにする**（作成・デタッチ時に既定 SG を必ず残す）方が安全。現状は SG を全部外すと無フィルタに戻れてしまう。
4. VLAN 切替は `network.yaml` の 1 行で済む設計になっているのは良い。物理作業の優先度を上げる価値がある。

### 3.4 監視・通知が 1 つもない

**事実:** リポジトリ全体で Prometheus / Grafana / Loki / Alertmanager / Uptime Kuma / netdata / zabbix のいずれも配備物として存在しない（ヒットするのは Flux の同梱マニフェストと設計文書の「将来」記述のみ）。

**評価:** 以下が**誰にも通知されない**:
- SSD の SMART 劣化（現在 Percentage Used 0% だが、書き込み 768GB は増え続ける）
- thin pool の枯渇（現在 29% だが**シンプロビジョニングなので論理合計は既に物理を超えうる**。thin pool が満杯になると VM が read-only に落ちる。ここが一番怖い）
- バックアップ timer の失敗（`Persistent=true` で次回は走るが、失敗が続いても静か）
- Let's Encrypt の更新失敗（DNS-01 なので Cloudflare トークン失効で静かに止まる）
- Flux の reconcile 失敗
- OOM / ホストのメモリ逼迫（割当合計 60.1GiB > 物理 59.7GiB）

**提案（軽い順）:**
1. **今日できる**: 全 systemd timer/service に `OnFailure=` を付けて ntfy か Gmail（既に SMTP 設定済み）へ飛ばす。5 行で「失敗が静かに続く」が消える。
2. `smartd` を Proxmox ホストへ（`smartd.conf` にメール宛先）。thin pool は `lvs` を cron で閾値監視。
3. 既存ラズパイに **Uptime Kuma** 1 個。HTTP と TCP の死活＋証明書期限＋Push monitor（バックアップ成功時に ping）で、K11 が死んでも K11 の外から気づける。設計文書の「監視は既存ラズパイと連携する」の最小実装。
4. Prometheus/Grafana は**その後**。保持期間を短く（15日）すれば容量は問題にならないが、まず 1〜3 の費用対効果が圧倒的に高い。

## 4. 高（P2）

### 4.1 NetBox の書き込みトークンが平文 HTTP を流れる
Terraform（`10-platform`）・Ansible 動的インベントリ・クラウド API が `http://192.168.10.200:8000` を使う（`netbox.sops.yaml.example`・`cloudapi.sops.yaml`・bootstrap.md で確認）。`https://netbox.apextox.dpdns.org` が既にあるのだから、**接続先をそちらへ統一し、8000 は 127.0.0.1 へ戻す**のが素直。同一 L2 に利用者 VM が居る（3.3）ので、ARP スプーフィングでトークンが取れる構図になっている。

### 4.2 NetworkPolicy が 1 つもない
`platform/flux/` に NetworkPolicy / CiliumNetworkPolicy が存在しない。とくに **`functions` namespace は Knative で利用者のコードが動く**。Cilium は入っているので、`functions` に default-deny（egress は DNS と明示先のみ）を置くのは安価。`databases` namespace の CNPG も同様。設計文書（operations.md）に「NetworkPolicy を設定する」と書いてあるので、意図と実装のギャップ。

### 4.3 コンテナのメモリ・CPU 制限がゼロ
全 `compose*.yaml` に `mem_limit` も `deploy.resources` も無い。`healthcheck` があるのは 16 ファイル、`restart: unless-stopped` は 40 箇所と良いが、**制限が無いので 1 コンテナの暴走が VM 全体を持っていく**。cloud-01 は 2GiB、storage-s3 は 1GiB と小さいので効きやすい。AWX の Pod には `requests` があるが `limits` が無い（`awx-instance/awx.yaml`）。
- 最低限 DB・Authentik worker・Nextcloud php・ollama に `mem_limit` を入れる。
- ホストは既に**割当合計 60.1GiB > 物理 59.7GiB** のオーバーコミット状態。バルーニング前提は文書化されているが、**先に倒れるのが基盤 VM** だと自分で書いているとおりのリスク。

### 4.4 Cloudflare DNS 編集トークンが全ホストに配られている
`roles/tls_proxy` が各ホストへ `cloudflare_dns_api_token` を置き、各 Caddy が DNS-01 で証明書を取る。**1 台侵害 = ゾーン全体の DNS 書き換え権限**（＝任意の名前で LE 証明書を取られる＋メールの乗っ取り経路）。「identity を他ホストの障害に巻き込まない」という分散の理由は妥当なので、対策は分散をやめることではなく:
- トークンを **Zone:DNS:Edit をこのゾーンだけ**にスコープ（既にそうならそれを文書へ明記）
- 可能なら `_acme-challenge` の CNAME 委譲（acme-dns 等）で、DNS 編集権限そのものを配らない
- 最低でもトークンのローテーション手順と最終ローテ日を `handover.md` に持つ

### 4.5 UPS 未接続、かつ自動シャットダウン連携なし
`docs/operations/power.md` は状態を「実機はまだ UPS 経由にしていない」と正直に書いていて、手順も良い。ただし **手順書は人が家に居るときしか効かない**。PostgreSQL（管理DB・Authentik・NetBox・CNPG）と SQLite（Vaultwarden・Kavita）を抱えたホストで突然の電源断は、3.1 のバックアップが無い状態と組み合わさると最悪。
- UPS 導入と同時に **NUT（`nut-client`）を Proxmox ホストへ**。`SHUTDOWNCMD` を `tools/k8s down && shutdown -h now` 相当にすれば、既にある停止順の知識をそのまま使える。
- UPS 到着前でも、`shutdown` 順の自動化（`tools/k8s down` を含む 1 スクリプト化）だけ先にやっておくと当日が楽。

### 4.6 依存更新の自動化が無い（文書は Renovate 前提）
`.github/` に `renovate.json` も `dependabot.yml` も無い。一方 `docs/architecture/operations.md` と `00-bootstrap/versions.tf` のコメントは「Renovate の PR で更新を確認する」と書いている。**digest 固定＋更新の仕組み無しは「固定されたまま古くなる」**。CI に脆弱性スキャン（`govulncheck` / `pip-audit` / `trivy`）も無い。
- `renovate.json` を置く（docker-compose・gomod・terraform・github-actions の manager を有効化）。`compose.lock.yaml` を digest 固定に使っているので、Renovate の digest pinning と相性が良い。
- CI に `govulncheck ./...` を 1 ステップ足すのは安い（Go コードが本体なので効果が高い）。

## 6. 良い点（維持すべき設計）

ここは「直すな」という意味で列挙する。

- **`handover.md` の「確定した決定」表**。理由と実測（Proxmox の 403 が「無い」を意味しない、チャンク転送 501、ルール挿入が pos 0 になる、`/tmp` が tmpfs）まで残っている。**引き継ぎ資産としてリポジトリで一番価値が高い。**
- **OpenAPI を正本にし、Go のルート表との一致を `routes_test.go` で強制**。コード生成をしない判断と、その代わりの検証を用意した点がセット。
- **noVNC を CDN ではなく同梱**（npm の sha512 照合・無改変・`PROVENANCE.md`・CSP `script-src 'self'`）。サプライチェーンの扱いとして正しい。
- **コンソールの防御**: Cookie 認証の WebSocket に Origin チェック（`CrossOriginProtection` が GET を見ないことを理解した上での追加実装）、5 分トークン、メモリ上もハッシュ、アクセスログに出さない、`Cache-Control: no-store`。設計として隙がない。
- **Go 1.27 の `http.NewCrossOriginProtection()`** を素の `net/http` で使い、CLI（Origin なし）は通す設計。
- **`tools/check-publication.py`**: 実際の `.env`・secrets から needle を作って staged blob を検査し、未暗号化 `.sops.yaml` と鍵パターンも弾く。CI で毎回走る。
- **`.gitignore` が deny-by-default**（`platform/sops/*` を全除外して 3 種だけ否定パターンで追跡）。「復号した平文を誤って add できない」という設計意図どおり。
- **Terraform state を Cloudflare R2 へ**（ミニ PC の SSD 1 枚に依存させない）＋ `use_lockfile = true`（R2 でロックが効く）＋ backend に事業者固有値を書かず `tools/tf` が SOPS から渡す。
- **`tools/pve-restore-drill.sh`**: 復元先の NIC を切断してから起動する、既存 VM を消さない、cleanup だけ確認を求める。ドリル用ツールとして作法が正しい。
- **冪等性と既存秘密値の保護**を全 `manage.py` が守り、テストで検証している。
- **CI の網羅**: 588 の Python テスト、全 tracked YAML のパース、Terraform fmt/validate（全 root module）、gofmt、go vet、go test（実 Postgres サービス付き）、yamllint、公開チェック、mkdocs --strict。ホームラボの CI としては過剰なくらい良い。
